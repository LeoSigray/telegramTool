# telegramTool HTTP API

Опциональный HTTP-слой поверх существующего CLI. Позволяет запускать рассылки/получать
статус из внешнего приложения (например — мобильной CRM).

## Запуск

```bash
pip install -r requirements.txt

# Сгенери токен и положи в .env
echo "API_TOKEN=$(openssl rand -hex 32)" > .env

./run_api.sh
# слушает 0.0.0.0:9000
```

Swagger UI: http://127.0.0.1:9000/docs

## Аутентификация

Каждый запрос (кроме `/health`) требует заголовок:

```
Authorization: Bearer <API_TOKEN>
```

## Endpoints

| Метод | Путь                              | Назначение                                      |
|-------|-----------------------------------|-------------------------------------------------|
| GET   | `/health`                         | Без авторизации; статус сервера                 |
| GET   | `/accounts`                       | Список аккаунтов из `sessions/`                 |
| GET   | `/accounts/check`                 | Проверить авторизацию (медленно)                |
| POST  | `/broadcast/chat/start`           | Запустить рассылку по чатам                     |
| GET   | `/broadcast/jobs`                 | Список запущенных и завершённых задач           |
| GET   | `/broadcast/jobs/{id}`            | Детали задачи (цели, лог)                       |
| POST  | `/broadcast/jobs/{id}/stop`       | Мягко остановить                                |
| DELETE| `/broadcast/jobs/{id}`            | Удалить запись о завершённой задаче             |

### POST /broadcast/chat/start

```json
{
  "message": "Привет! ...",
  "targets": ["@chat1", "https://t.me/chat2", "+abcdef..."],
  "parallel": 2
}
```

Возвращает `Job` с `id`. Прогресс смотрится через `GET /broadcast/jobs/{id}?include_log=true`.

## Webhook входящих сообщений (опционально)

Если задать `CRM_WEBHOOK_URL` и `CRM_WEBHOOK_TOKEN` — при старте сервера
поднимется listener: подключит все аккаунты из `sessions/` и при каждом
**входящем личном сообщении** будет POST'ить в этот URL:

```json
{
  "account_name": "+380981257112",
  "platform_user_id": "12345678",
  "username": "ivan",
  "display_name": "Ivan",
  "phone": null,
  "chat_id": "12345678",
  "message_id": "9876",
  "text": "Привет",
  "from_me": false,
  "sent_at": "2025-..."
}
```

Заголовок: `Authorization: Bearer $CRM_WEBHOOK_TOKEN`.

CRM-бэк в этом проекте принимает webhook на `/external/incoming` — у него
переменная `EXTERNAL_API_TOKEN` должна совпадать с `CRM_WEBHOOK_TOKEN` здесь.

## Платформа диалогов (`/inbox`)

Отдельный экран для переписки с людьми, которые **ответили** на рассылку.

Как это работает:

- Рассылка сама по себе диалог **не создаёт**. Диалог появляется в момент,
  когда получатель рассылки пишет в ответ (`listener` ловит входящее, матчит
  его с записью в `sends` и заводит диалог в `inbox_conversations`).
- После первого ответа в диалог складываются **все** сообщения в обе стороны:
  входящие, исходящие с платформы и исходящие, отправленные вручную из самого
  Telegram.
- При открытии диалога подтягивается реальная история переписки из Telegram
  (последние ~50 сообщений) — чтобы был виден весь контекст.
- Ответ оператора уходит **с того же аккаунта**, с которого шла рассылка этому
  человеку. Если аккаунт недоступен (не в пуле / отдыхает / забанен) — берётся
  любой активный аккаунт, и диалог «переезжает» на него.

| Метод | Путь                                   | Назначение                                  |
|-------|----------------------------------------|---------------------------------------------|
| GET   | `/inbox` (без токена, HTML)            | Страница-мессенджер (как `/dashboard`)      |
| GET   | `/inbox/stats`                        | Счётчики: открытых / непрочитанных          |
| GET   | `/inbox/conversations?status=&q=`      | Список диалогов (`status`: open/closed/all) |
| GET   | `/inbox/conversations/{id}`           | Диалог + лента сообщений (+гидрация истории) |
| POST  | `/inbox/conversations/{id}/reply`     | Отправить ответ (`{"text": "..."}`)         |
| POST  | `/inbox/conversations/{id}/read`      | Пометить прочитанным                         |
| POST  | `/inbox/conversations/{id}/status`    | `{"status": "open"\|"closed"}`              |
| POST  | `/inbox/conversations/{id}/hydrate`   | Принудительно перечитать историю из Telegram |
| POST  | `/inbox/backfill`                     | Посеять диалоги из истории рассылок          |

Данные лежат в том же `data/database.db` (`inbox_conversations`, `inbox_messages`).
В десктоп-дашборде это пункт «📨 Диалоги» — он открывает ту же страницу `/inbox`
во встроенном фрейме.

## Нейросеть (генерация текста)

Нейрокомментинг, имена/фамилии, варианты рассылки и AI-редактор идут через
`api/llm.py` — единый слой. Модель задаётся на КЛАСС задачи строкой
`провайдер:модель`:

```
LLM_FAST=openrouter:nvidia/nemotron-3-super-120b-a12b:free    # объём: нейрокомментинг, имена
LLM_SMART=openrouter:nvidia/nemotron-3-super-120b-a12b:free   # качество, редко: варианты рассылки, AI-редактор
OPENROUTER_API_KEY=...                                        # бесплатно, без карты — openrouter.ai/keys
```

Провайдеры: `openrouter`, `groq`, `grok`, `claude`, `deepseek`, `cerebras`,
`openai`, `ollama` (локально). `openrouter`/`groq`/`grok`/`deepseek`/… — один
OpenAI-совместимый бэкенд, отличается только базовым URL и ключом. Примеры:
`LLM_SMART=deepseek:deepseek-v4-pro`, `LLM_FAST=ollama:qwen2.5:14b`.

Совместимость: старый `LLM_PROVIDER=claude` (без `LLM_FAST/SMART`) тоже
работает — применяется к обоим классам.

> Gemini как провайдер убран из кода (не было доступа к API). Groq (`groq`)
> и Grok (`grok`, платный, xAI) тоже поддерживаются, но по умолчанию —
> OpenRouter: Groq оказался недоступен напрямую с некоторых сетей
> ("All connection attempts failed"), OpenRouter обычно доступнее.

### AI-редактор текстов рассылки

Замыкает петлю обучения: бандит (`optimizer/bandit.py`) статистически
находит лидера/аутсайдеров среди вариантов текста → нейросеть получает эту
статистику + **реальные ответы людей** + фразы отказов и предлагает новые
варианты и «шкалу тона». Никакого дообучения модели — «обучение» это цикл
бандит → нейросеть → человек добавляет вариант → бандит.

| Метод | Путь                              | Назначение                                       |
|-------|-----------------------------------|--------------------------------------------------|
| GET   | `/analytics/copy/analyze?niche=`  | Разбор ниши: инсайты, новые варианты, шкала тона. Один вызов = один запрос к SMART-модели. Ничего не сохраняет. |
| POST  | `/analytics/copy/apply`           | `{"niche": "...", "texts": [...]}` — сохранить выбранные варианты как шаблоны → в бандит |

В десктоп-дашборде это пункт «🧠 AI-редактор текстов».

## Заметки

- Хранение задач — **в памяти процесса**. Перезапустишь сервер — список задач пуст
  (но дневные счётчики и состояние сессий не теряются).
- Все клиенты живут в общем пуле. broadcast-задачи **не создают новые
  подключения** — пользуются пулом (поэтому listener продолжает ловить ответы
  во время и после рассылки).
- Лимиты (`CHAT_DELAY_*`, `JOIN_DELAY_*`, дневные, `DM_LIMIT_PER_ACCOUNT`)
  берутся из `config.py` / `data/daily_limits.py` — те же что и у CLI-версии.
