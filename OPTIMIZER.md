# Оптимизатор рассылки

Задача: **больше лидов за меньшие деньги**. Ниже — как это устроено и как этим пользоваться.

## Главная формула

```
                 цена аккаунта / сколько сообщений он успеет отправить
CPL  =  ─────────────────────────────────────────────────────────────────
                    reply_rate  ×  доля ответов, ставших лидом
```

Из неё видно два рычага:

| Рычаг | Эффект на CPL | Побочный эффект |
|---|---|---|
| Аккаунт живёт дольше | ↓ пропорционально | — |
| Reply rate вырос вдвое | ↓ **вдвое** | нужно вдвое меньше отправок → аккаунты живут дольше |

Второй рычаг сильнее: он снижает цену лида **и** нагрузку одновременно. Поэтому система вкладывается в качество текста и чистоту списка, а не в наращивание темпа.

## Три независимых контура

Их намеренно не смешивают в одну reward-функцию. Если считать «бан» просто отрицательной наградой, алгоритм будет неделями «изучать» агрессивный темп, теряя аккаунты. Безопасность — жёсткий отдельный контур с приоритетом.

```
┌─ optimizer/health.py ──── БЕЗОПАСНОСТЬ ──────────────────────────┐
│  сколько сообщений сегодня можно дать каждому аккаунту           │
│  реагирует на ОШИБКИ, не на лиды. Умеет только тормозить.        │
└──────────────────────────────────────────────────────────────────┘
┌─ optimizer/bandit.py ──── КАЧЕСТВО ──────────────────────────────┐
│  какой из вариантов текста слать следующему контакту             │
│  Thompson Sampling по reply-rate                                 │
└──────────────────────────────────────────────────────────────────┘
┌─ optimizer/economics.py ─ ДЕНЬГИ ────────────────────────────────┐
│  во сколько обходится лид и стоит ли докупать аккаунт            │
└──────────────────────────────────────────────────────────────────┘
                              ↓
                    optimizer/planner.py — дневной план
```

## 1. Чистка списка (самая дешёвая оптимизация)

`planner.clean_targets()` перед каждым запуском убирает:

- **дубли** внутри загрузки;
- **стоп-лист** — кто ответил «не пишите / спам / отпишись». Пополняется автоматически из `api/listener.py`;
- **тех, кому уже писали когда-либо** — повторное сообщение почти не конвертит, но стоит денег и порождает жалобы.

Ничего не удаляется молча: `POST /analytics/plan` показывает, что и почему отсеялось, ещё до запуска.

## 2. Динамический лимит на аккаунт

Было: `DM_LIMIT_PER_ACCOUNT = 20` — одинаково для свежекупленного и для работающего месяц.

Стало:

```
cap = 25 (база) × ramp(возраст) × multiplier(история ошибок),  потолок 35
```

- **ramp** — новый аккаунт стартует с 20% и выходит на полную за ~2 недели;
- **multiplier** — падает **вдвое** при FloodWait/PeerFlood и восстанавливается на +10% за чистый день, но **никогда не превышает 1.0**. Контур умеет только притормаживать и возвращаться к норме;
- при жёсткой ошибке аккаунт уходит «отдыхать»: PeerFlood — 48 ч, FloodWait — 12 ч, бан — навсегда (`status='dead'`).

Тем самым нагрузка сама перетекает на здоровые аккаунты, а проблемные выводятся из ротации до того, как их потеряют.

## 3. A/B текстов — Thompson Sampling

Наивный подход «50/50 и через неделю посмотрим» тратит половину бюджета на слабый вариант всё это время.

Для каждого варианта держим `Beta(1 + ответы, 1 + молчания)`. Перед отправкой берём случайную выборку из каждого распределения и шлём тем, у кого она выше. Доля трафика автоматически становится пропорциональна вероятности, что вариант — лучший.

На симуляции 600 отправок (вариант A истинно 5%, B истинно 14%):

```
A: отправлено  51   ответов  2   rate 3.9%
B: отправлено 549   ответов 74   rate 13.5%     P(B лучший) = 97.7%
```

Слабый вариант отмер за полсотни отправок, а не за неделю.

Защита от преждевременного схлопывания: пока какой-то вариант не набрал `MIN_SAMPLES = 30` решённых исходов, ему принудительно отдаётся трафик — иначе бандит закрепится на том, кому повезло на первых трёх отправках.

**Что считается успехом:** ответ в течение 72 часов (`REPLY_WINDOW_HOURS`). Молчание превращается в «неудачу» только после истечения окна — свежие отправки статистику не портят.

## 4. Размер волны

`planner.wave_size()` не даёт вывалить весь список сразу:

- **learning** — пока варианты без статистики, волна ограничена объёмом, нужным для их различения;
- **exploit** — статистика собрана, шлём победителем, ограничение только по ёмкости пула.

## 5. Решение о покупке аккаунта

Обычная маржинальная проверка (`economics.should_buy_account`):

```
покупаем, если:  ожидаемый_пробег × P(лид с сообщения) × ценность_лида  >  цена аккаунта
```

`GET /analytics/buy-decision?value_per_lead=1500` вернёт `buy`/`hold`, ожидаемую выручку и цену безубыточности.

## Порядок внедрения

### 1. Проставить цену аккаунтов — без неё CPL не считается

```bash
curl -X POST localhost:9000/analytics/accounts/acc1/cost \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"cost": 22, "source": "lzt"}'
```

### 2. Завести 2–3 варианта текста на нишу

```bash
curl -X POST localhost:9000/analytics/templates \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"niche":"стоматологии","text":"Добрый день! ..."}'
```

Тексты генерируются нейронкой (`api/llm.py`, провайдер Grok по умолчанию) — просто сгенерируйте **два разных**, а не один, и залейте оба. Дальше бандит сам решит.

### 3. Посмотреть план, ничего не отправляя

```bash
curl -X POST localhost:9000/analytics/plan \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"targets":["@a","@b"],"niche":"стоматологии","value_per_lead":1500}'
```

### 4. Запустить рассылку с оптимизатором

```bash
curl -X POST localhost:9000/broadcast/dm/start \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"targets":["@a","@b"],"niche":"стоматологии","parallel":3,"optimize":true}'
```

`message` не нужен, если задана `niche` с шаблонами.

### 5. Возвращать исходы из CRM — иначе CPL останется модельным

`api/listener.py` кладёт в вебхук поле `send_id`. Когда контакт стал лидом:

```bash
curl -X POST localhost:9000/analytics/outcome \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"send_id": 123, "outcome": "lead"}'
```

Это замыкает петлю: бандит начинает оптимизировать не просто ответы, а реальные лиды.

## Аналитика

Живой дашборд: **`http://localhost:9000/dashboard`** (токен вводится на странице, обновление каждые 5 сек).

Эндпоинты для вашей CRM:

| Endpoint | Что отдаёт |
|---|---|
| `GET /analytics/overview` | всё для шапки одним запросом |
| `GET /analytics/funnel` | воронка: попытки → доставлено → ответы → лиды |
| `GET /analytics/timeseries` | отправлено/ответов/ошибок по дням |
| `GET /analytics/templates?niche=` | A/B: reply-rate, доверительные интервалы, `P(лучший)` |
| `GET /analytics/accounts` | здоровье аккаунтов, лимиты, ошибки |
| `GET /analytics/cpl`, `/cpl/by-niche` | цена лида фактическая и модельная |
| `GET /analytics/buy-decision` | покупать ли ещё аккаунт |
| `GET /analytics/forecast` | сроки и бюджет на остаток списка |
| `POST /analytics/outcome` | исход из CRM |
| `POST /analytics/suppress` | ручное добавление в стоп-лист |

## Схема данных

Всё в том же `data/database.db`:

- `sends` — каждая отправка + исход (`pending → replied/no_reply/negative/lead`);
- `templates` — варианты текста по нишам;
- `account_meta` — цена, возраст, статус, множитель лимита;
- `account_events` — журнал FloodWait/PeerFlood/банов;
- `suppression` — стоп-лист.

Ключевая связка: `sends.peer_id` ← listener матчит входящее по telegram user_id и проставляет `replied_at`. Без неё reply-rate, а значит и цена лида, не считаются в принципе.
